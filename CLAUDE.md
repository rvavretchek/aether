# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This is a **BMAD Method v6.10.0** installation for a project named **Aether** — a planned full-stack framework (React.js frontend + Node.js backend). As of now the repository contains **no application source code**: it is a planning/orchestration scaffold. `Aether.md` is the working vision document (in Portuguese) — a Must/Should/Can feature matrix for a modular-monolith framework with a "Skill Registry" + SDD (Skill-Driven Development) orchestrator, plus Mermaid architecture and sequence diagrams. There is no `package.json` anywhere yet; nothing to build, lint, or test until implementation actually starts.

Because there's no code yet, work in this repo mostly means **running BMAD Method skills** (analysis → planning → solutioning → implementation workflows) rather than editing source files directly. Once real application code is scaffolded (via `bmad-architecture` / `bmad-quick-dev` / `bmad-dev-story` etc.), update this file with real build/lint/test commands and architecture notes for that codebase.

## Project configuration (important — affects every interaction)

- **Communication language**: `Português do Brasil` — set in `_bmad/core/config.yaml` (`communication_language`) and mirrored in every module config. All conversation and all documentation (PRDs, briefs, architecture docs, comments in docs, etc.) must be in Brazilian Portuguese.
- **Code language**: once implementation starts, all code identifiers — variables, constants, classes, functions, files, etc. — must be in **English**. Only conversation and documentation stay in pt-BR; the codebase itself follows standard English naming conventions.
- **User name** (in BMAD config): `Boss`.
- Config precedence: `_bmad/config.toml` and `_bmad/*/config.yaml` are **installer-managed** — regenerated on every `bmad install`/update, treat as read-only, do not hand-edit. Durable overrides go in `_bmad/custom/config.toml` (team-shared, committed) or `_bmad/custom/config.user.toml` (personal, gitignored). Neither of those is touched by the installer.

## Project goals

1. **Objetivo principal**: agregar um projeto interessante e demonstrável ao portfólio do autor.
2. **Objetivo secundário**: construir um framework monolítico React.js + Node.js de uso geral que já embarque funcionalidades importantes (auth, validação, ORM/migrations, etc. — ver `Aether.md`) para reduzir o tempo de desenvolvimento de projetos futuros, e que seja **facilmente manipulável por agentes de IA** (Claude Code, Codex, etc.) — convenções previsíveis, estrutura modular clara, documentação e specs que um agente consiga consumir diretamente.

`Aether.md` é o **ponto de partida** para o desenho do produto (brainstorm inicial), não a especificação final — espera-se que evolua/seja substituído pelos artefatos formais do BMAD (brief, PRD, arquitetura) conforme o projeto avança.

## Repository layout

- **`_bmad/`** — the BMAD Method installation itself: per-module config (`core`, `bmm`, `bmad-loop`, `tea`, `bmb`, `cis`, `gds`, `wds`), manifests (`_bmad/_config/manifest.yaml` lists installed module versions/sources, `bmad-help.csv` / `skill-manifest.csv` catalog every skill with its phase and menu code), and helper scripts (`_bmad/scripts/`).
- **`.claude/skills/`, `.agent/skills/`, `.agents/skills/`, `.qwen/skills/`, `.opencode/commands/`, `.github/agents/`** — installer-generated **mirrors of the same BMAD skill set** for different IDEs/agents (Claude Code, generic agent runners, Qwen, OpenCode, GitHub Copilot). `.claude/skills/` is the one Claude Code loads. Skills are named `bmad-*`, `gds-*` (Game Dev Studio module), or `wds-*` (Web Design Studio module). Don't hand-edit skill content in one mirror expecting it to propagate — these are regenerated by the installer/`sync` skill.
- **`_bmad-output/`** — where BMAD workflows write their artifacts, currently empty:
  - `planning-artifacts/` — briefs, PRDs, UX designs, architecture docs (phases 1–3: analysis/planning/solutioning)
  - `implementation-artifacts/` — sprint plans, stories, retrospectives (phase 4: implementation)
  - `test-artifacts/` — TEA module output: test design, test reviews, traceability matrices
- **`design-artifacts/`** — WDS (Web Design Studio) phase folders, currently empty: `A-Product-Brief`, `B-Trigger-Map`, `C-UX-Scenarios`, `D-Design-System`, `E-Development`.
- **`docs/`** — intended home for project knowledge (`project_knowledge` in `bmm`/`gds`/`wds` configs); currently empty.
- **`Aether.md`** — the standing product vision doc: feature matrix (Must/Should/Can) for the target framework and two Mermaid diagrams (modular-monolith component architecture, SDD orchestration sequence flow). Treat as the north star when running planning workflows, not as implemented behavior.

## Working with BMAD skills

Skills are invoked as `bmad-*`/`gds-*`/`wds-*` via the Skill tool (or as slash commands in other IDEs). `_bmad/_config/bmad-help.csv` is the authoritative catalog: each row gives the module, skill, action, workflow **phase** (`1-analysis`, `2-planning`, `3-solutioning`, `4-implementation`, or `anytime`), its `preceded-by`/`followed-by` sequencing, and output location. Use `bmad-help` to get a live menu, or read that CSV directly, when deciding which skill applies.

Typical software-development flow (module `bmm`), in order: `bmad-brainstorming` / `bmad-product-brief` or `bmad-prfaq` (analysis) → `bmad-prd` + `bmad-ux` (planning) → `bmad-architecture` → `bmad-create-epics-and-stories` → `bmad-check-implementation-readiness` (solutioning) → `bmad-sprint-planning` → `bmad-create-story` → `bmad-dev-story` → `bmad-code-review` → `bmad-retrospective` (implementation, looped per story/epic). `bmad-quick-dev` is a lighter unified intent-to-code path for anytime use. The **WDS** module (`wds-*`) offers a parallel, UX-first pipeline (`wds-0-project-setup` → `wds-1-project-brief` → `wds-2-trigger-mapping` → `wds-3-scenarios` → `wds-4-ux-design` → `wds-5-agentic-development` → ...) writing into `design-artifacts/`.

Named BMAD personas (Mary/analyst, John/PM, Sally/UX, Winston/architect, Amelia/dev, Murat/test architect, Paige/tech writer, Freya/Saga/Mimir for WDS, etc.) are defined per-agent in `_bmad/config.toml` under `[agents.*]` — invoked via the corresponding `bmad-agent-*` / `wds-agent-*` skill.
