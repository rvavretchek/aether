- (note) Insumos: PRD final (prd-Aether-2026-08-11, todos os FRs/NFRs já resolvidos, sem suposição pendente), Architecture Spine finalizada (architecture-Aether-2026-08-14, 10 ADs + Reviewer Gate aplicado), companion UML (docs/architecture-uml-Aether.md). Entrada rica e pré-organizada — extração direta, sem elicitação de campo a campo.
- (capability) CAP-1 — Scaffolding e ambiente local de zero a Hello World. intent: dev cria e sobe projeto completo (front+back+banco+capturador email) sem editar config à mão. success: new->setup banco->dev em <=3 comandos, Hello World com banco conectado, replicável só com documentação (PRD FR-1..FR-6, SM-1/SM-2).
- (capability) CAP-2 — Scaffolding de Módulo via generate. intent: dev gera Módulo de domínio completo (schema+validação+router protegido+Recursos+teste) num comando, 1+ nomes de uma vez, ou em lote via arquivo. success: generate module <nomes...> produz os 4 arquivos-adapter + domain/ + teste por nome, já registrado como nó na árvore, sem passo manual (FR-3, FR-21).
- (capability) CAP-3 — Autenticação robusta e extensível. intent: usuário autentica via JWT+Refresh+Argon2id/Pepper através de AuthProvider trocável. success: access token em memória + refresh em cookie httpOnly/SameSite; token expirado rejeitado; excesso de tentativas bloqueia temporariamente; trocar AuthProvider/SecretsProvider não toca código consumidor (FR-7..FR-10, FR-26, FR-28).
- (capability) CAP-4 — Árvore de identidade hierárquica com enforcement em runtime. intent: Usuário/Grupo/Papel/Módulo como objetos de 1a classe, herança aditiva de permissão aplicada em tempo real, default-deny. success: chamada tRPC rejeita usuário sem o Recurso antes de qualquer lógica de negócio; papel propaga a descendentes; ancestralidade sem N+1 (Closure Table); nenhuma query vaza dado de outro Tenant (FR-11..FR-13, FR-27).
- (capability) CAP-5 — Administração funcional de identidade. intent: admin visualiza/cria/edita/remove/organiza Usuário/Grupo/Papel, importa em lote, revoga sessão. success: organizar N usuários em M grupos/papéis exige O(M) ações via seleção múltipla, nunca O(N); import CSV reporta sucesso/erro por linha; revogar sessão pela tela invalida refresh token imediatamente; toda ação reflete na árvore sem sync manual (FR-14, FR-15, FR-9, SM-4).
- (capability) CAP-6 — Comunicação tipada ponta a ponta. intent: frontend consome API só via tRPC, validação Zod compartilhada sem duplicação. success: mudança de assinatura de procedure gera erro de tipo no frontend em compile-time sem gerador de client; input inválido rejeitado com erro RFC 9457 antes de lógica de negócio (FR-16, FR-17).
- (capability) CAP-7 — Notificações transacionais. intent: email transacional (import usuário, reset senha) via interface unificada, capturado localmente em dev. success: link de reset usa token de uso único expirável; completar reset invalida todas sessões ativas; em dev todo email é capturado por Mailpit local sem envio real (FR-18..FR-20).
- (capability) CAP-8 — Qualidade, observabilidade e DX de fábrica. intent: projeto gerado nasce com testes, lint, Docker dev, logging estruturado correlacionado, erro global tratado. success: projeto novo passa lint/format sem alteração manual; toda requisição loga JSON com traceparent; erro não tratado não derruba processo, retorna RFC 9457 com invalid-params (FR-21..FR-25).
- (constraint) tRPC é o único mecanismo de comunicação frontend<->backend, sem REST/GraphQL alternativo nem pra casos especiais (upload usa FormData/Blob como input tRPC, nunca endpoint multipart paralelo). Fonte: FR-16, AD-3.
- (constraint) Cada Módulo de negócio segue Hexagonal: domain/ sem import de Prisma/tRPC; domain-a-domain entre módulos diferentes proibido, só via router ou porta explícita. Fonte: AD-1.
- (constraint) Todo acesso a dado escopado por Tenant passa pela extensão Prisma consciente de tenant; $queryRaw/$executeRaw proibidos em repository de módulo de negócio. Fonte: AD-5, NFR §8.1.
- (constraint) Enforcement de permissão é default-deny via middleware central; resource-id é sempre <module-slug>.<ação>, único globalmente, geração falha explicitamente em colisão. Fonte: AD-7, FR-27.
- (constraint) ModuleClosure é append-only no MVP — sem reparent/move de Módulo pós-criação. Fonte: AD-6.
- (constraint) Nenhuma implementação MVP depende de Redis (TokenRevocationStore, rate limiting, cache de permissão) — Postgres-backed ou sem cache. Fonte: NFR §8.1, AD-8, AD-10.
- (constraint) Interfaces de extensão (AuthProvider, SecretsProvider, TokenRevocationStore, e qualquer futura) são instanciadas só em providers.ts; código de negócio nunca importa implementação concreta, só via ctx tRPC. Fonte: AD-4.
- (constraint) Herança de Papel é aditiva simples — sem bloqueio/override por nó no MVP. Fonte: FR-12, decisão compartilhada com o Tecton.
- (constraint) Isolamento de tenant (base compartilhada vs. banco dedicado) é sempre escolha do desenvolvedor, nunca imposta pelo framework. Fonte: FR-2, §8.1.
- (constraint) Sem alvo de deploy de produção no MVP — só ambiente de dev local via Docker Compose. Fonte: AD-9, PRD §6.2.
- (decision) Non-goals (PRD §5 + Architecture Deferred): framework de microsserviços (é o Tecton); gerador genérico de CRUD pra entidade de negócio arbitrária; REST/GraphQL como alternativa a tRPC; bloqueio/override de herança por nó; árvore visual drag-and-drop; auth plugável (Keycloak/OpenBAO) implementada; deploy/infra de produção e pipeline CI/CD; cache/Redis, filas assíncronas, i18n; KeyCustodyProvider e WorkflowEngineProvider implementados (só interface prevista).
- (decision) Success signal: um desenvolvedor React+Node desconhecido do projeto, sem o autor por perto, só com documentação, vai de aether-admin new a Hello World funcional (banco conectado, servidor rodando) em no máximo 3 comandos — testável com 3-5 pessoas reais (PRD SM-1/SM-2). O mesmo desenvolvedor organiza um cenário tipo UJ-2 (dezenas de usuários em grupos/papéis) em O(M) ações de seleção múltipla, nunca uma ação por pessoa (SM-4).
- (assumption) resource-id segue <module-slug>.<ação> — decisão do arquiteto durante o reviewer gate da spine (achado adversarial de colisão de nome), não confirmada literalmente pelo usuário em coaching direto.
- (assumption) Resolução de tenant pré-autenticação via input explícito tenantId/tenantSlug na procedure de login — sem host/subdomínio-based resolution no MVP; chamada do arquiteto pós-review, não coached diretamente.
- (assumption) Chave de assinatura JWT (jose) flui pelo SecretsProvider, mesmo caminho do pepper Argon2id — inferido por simetria com FR-8, não afirmado explicitamente pelo PRD.
- (assumption) Frontend usa loader de rota (React Router data router) + client tRPC direto, sem TanStack Query no MVP — decisão do arquiteto pra evitar duas fontes de cache/erro coexistindo, não coached diretamente.
- (assumption) RateLimitHit é tabela própria em core/auth, separada da tabela de revogação de refresh token — PRD só exige 'mesmo banco de dados' (sem Redis), não 'mesma tabela'; leitura mais estrita corrigida no reviewer gate da arquitetura.
- (question) Quais outros tipos além de module o aether-admin generate deve suportar (ex.: página, componente isolado)? PRD §11 sinaliza a pergunta sem enumerar (fica em aberto na spine também).
- (question) Convenção de UI/componentes/estilo (Tailwind vs CSS Modules vs kit) pras telas de admin (CAP-5) — sem artefato de UX ainda alimentando spec/spine.
- (question) Reparent/mover um Módulo após criado — hoje fora do MVP (ModuleClosure append-only); quando entrar em escopo, precisa de protocolo de escrita explícito (delete+reinsert vs. versionamento) ainda não desenhado.
- (event) Self-validate Pass 1 (coerência, Spec Law 1-6+8): OK. 8 capabilities com intent+success testável; 12 constraints todas bendendo decisão real; 10 non-goals; success signal concreto (<=3 comandos, 3-5 pessoas, O(M) ações); IDs CAP-1..CAP-8 estáveis/únicos; prosa enxuta.
