# Story 5.8: Import em lote de Usuários via CSV (FR-15)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

Como administrador,
eu quero enviar um arquivo CSV com uma lista de emails e ter um Usuário criado para cada linha válida — cada um recebendo o mesmo email de configuração de senha que `users.create` já envia hoje —,
para que eu não precise cadastrar usuários um por um quando for popular o tenant pela primeira vez (ex.: migração de uma base externa).

## Acceptance Criteria

1. Existe `adminRouter.users.bulkImport`, protegida por `requireAdmin()` (mesmo padrão de toda `adminRouter`), que aceita um `FormData` contendo um único campo de arquivo (CSV) — nunca um array JSON de emails. Transporte via `FormData`/`Blob` (AD-3), não um endpoint REST/multipart paralelo.
2. O CSV é interpretado com uma coluna `email` (header obrigatório na primeira linha — mesmo contrato que uma planilha exportada do Excel/Google Sheets produz por padrão); linhas totalmente vazias são ignoradas silenciosamente (artefato comum de exportação, não um erro).
3. Cada linha é processada de forma **independente** — uma linha invàlida (email mal formado) ou duplicada (já existe User com esse email no tenant) nunca aborta as demais linhas do lote. A procedure retorna, para cada linha de dados do CSV (na ordem original), um resultado `{ email: string; status: 'created' | 'duplicate' | 'invalid' }` (`email` no caso `invalid` é o valor bruto da célula, não normalizado, já que pode não ser um email de verdade).
4. Para cada linha `created`, o comportamento é **idêntico** ao de `users.create` (Story 5.1) — nenhuma senha real, hash placeholder via `ctx.authProvider.hash`, emissão de token via `ctx.passwordResetTokenStore.issue` e envio do email `account-setup` via `ctx.emailProvider.send`. Se o envio do email falhar para uma linha específica, essa linha desfaz o `User` recém-criado (mesmo tratamento de `users.create`) e aparece no resultado como `invalid` — mas as outras linhas do lote continuam processando.
5. O lote tem um limite explícito de **500 linhas de dados** (constante nomeada, não mágica) — acima disso, a procedure inteira rejeita com `BAD_REQUEST` **antes** de processar qualquer linha (nenhum efeito parcial num lote rejeitado por tamanho).
6. Nenhuma AC desta story exige UI — `apps/web` permanece sem nenhuma tela nova (mesmo corte de escopo das Stories 5.1-5.7); a procedure é validada via chamada direta (testes) e via probe script contra a API real, nunca via navegador.

## Dev Notes

### 🎯 Onde este código realmente vive — mesmo lembrete das Stories 1.1-5.7

Tudo em `apps/api/src/core/admin/...`/`packages/shared/...` nos Tasks acima é o caminho DENTRO do projeto que `aether-admin new` gera. O trabalho real é editar os templates deste repositório: `src/scaffolding/templates/admin.ts` (router + testes), `src/scaffolding/templates/shared.ts` (schema do resultado), `src/scaffolding/templates/api.ts` (dependência `csv-parse`).

### ⚠️ Escopo explicitamente cortado desta story

- **Nenhuma UI** — `apps/web` não ganha nenhuma tela/formulário de upload nesta story (mesmo corte de todas as Stories 5.1-5.7; a UI do admin como um todo está bloqueada numa decisão de UX/design, ver "Deferred" da Architecture Spine). A procedure é validada via teste direto (`createCaller`) e via um probe script que monta `FormData` real e chama a API real por HTTP — nunca via navegador.
- **`apps/web/src/trpc/client.ts` NÃO é tocado nesta story.** Ele hoje usa só `httpBatchLink` (ver `src/scaffolding/templates/web.ts`), que serializa todo input como JSON — não suporta `FormData` como input de procedure. Pra uma tela real de upload funcionar no browser, o client precisaria migrar pra `splitLink` com `isNonJsonSerializable`/`httpLink` (documentação oficial do tRPC v11, ver References) roteando só as chamadas não-serializáveis por `httpLink` e o resto continua batchado. Isso é trabalho de quem construir a tela de import (story futura de UI), não desta story — que é só o backend. Registrar esse gap aqui evita que a story de UI redescubra isso do zero.
- **Sem fila assíncrona/processamento em background** — 500 linhas sequenciais (Task 4.7) é um limite deliberadamente conservador pro MVP (sem Redis, NFR já estabelecido desde a Epic 2). Lotes maiores ou um job assíncrono de verdade ficam pra uma story de Roadmap, se a demanda real aparecer.
- **Sem relatório de erro por linha mais granular que `'invalid'`** (ex.: distinguir "email mal formado" de "falha no envio do email de setup") — a AC #3 só exige 3 estados; granularidade maior sem uma AC puxando por ela seria especulação.

### Arquitetura — o que seguir à risca

- **AD-3 (upload via FormData/Blob)**: "Upload de arquivo (ex.: import CSV, FR-15) usa suporte a FormData/Blob como input de procedure tRPC — nenhum endpoint REST/multipart paralelo, mesmo para esse caso." É LITERALMENTE esta story que a AD-3 cita como exemplo — a decisão arquitetural já está tomada, a story só implementa.
- **tRPC v11 — padrão oficial de input `FormData`** (confirmado contra a documentação atual, 2026): `.input(z.instanceof(FormData))` direto no router; o `AppRouter` tipado continua funcionando normalmente, `FormData` chega como objeto nativo no `input` do resolver. Fonte: `https://trpc.io/docs/server/non-json-content-types`.
- **O adapter Fastify do tRPC (`@trpc/server/adapters/fastify`, já em uso desde a Story 1.1) suporta `FormData`/corpo não-JSON — CONFIRMADO via validação real** (não só inferência de código-fonte): probe HTTP real contra o servidor rodando de verdade no Laboratório Integrit (login real → `accessToken` real → `POST multipart/form-data` real via `@trpc/client`'s `httpLink`, que detecta `FormData` e monta o multipart sozinho) criou 2 Users de verdade e disparou 2 emails `account-setup` reais, capturados pelo Mailpit real. Um issue antigo do próprio tRPC (2024, desatualizado) ainda aparece em buscas dizendo que o suporte a FormData era só dos adapters node-http standalone/express/next — o comportamento real desta versão (`@trpc/server: 11.18.0`) contradiz isso: o handler (`fastifyRequestHandler.ts`) converte o `IncomingMessage` bruto pra um `Request` padrão da Web API ANTES de qualquer parsing de JSON, e o corpo multipart chega intacto, sem `@fastify/multipart` nem plugin adicional.
- **`csv-parse` (`csv-parse/sync`)**: biblioteca madura e amplamente usada do ecossistema `csv.js.org`, ESM nativo (`import { parse } from 'csv-parse/sync'`), versão atual `7.0.3`. Mesma disciplina de "nunca parsing feito à mão" já aplicada a `argon2`/`jose`/`nodemailer` nas Stories 2.x/4.x.
- **AD-5 (isolamento de tenant)**: `createUserWithSetupEmail` recebe `tenantId` explícito (vem de `ctx.user.tenantId`, nunca inferido de outro lugar) e usa `forTenant(tenantId)` — mesmo padrão de `users.create`. A checagem de duplicata (AC #3/#5.11) é por constructo escopada ao tenant (o `@@unique` de `email` em `User` já é composto com `tenantId`, Story 2.1) — um email de OUTRO tenant nunca aparece como `'duplicate'`.
- **TS2742 real, achado durante a validação local (`tsc --build` contra um projeto gerado de verdade, não suposição)**: `z.instanceof(FormData)` direto no `.input()` quebra `tsc --build` (`composite`/`declaration`, exigido pra `apps/web` importar `type { AppRouter }`) com "The inferred type of 'adminRouter' cannot be named without a reference to '.pnpm/undici-types@.../node_modules/undici-types'". Causa raiz: `FormData.get()` retorna `FormDataEntryValue = string | File`, e esse `File` é importado por `undici-types` (dependência transitiva SÓ de `@types/node`) através de um caminho interno do pnpm store que o TypeScript não consegue nomear de forma portável ao emitir o `.d.ts` do router. **Duas tentativas de fix NÃO resolveram** (registradas aqui pra não serem retentadas): (1) adicionar `undici-types` como dependência direta de `apps/api` — não ajuda porque a referência ambígua que o `@types/node` usa (`/// <reference types="undici-types" />`) resolve pelo caminho mais próximo DELE mesmo, nunca pelo nosso `node_modules` sibling; (2) `publicHoistPattern: ['undici-types']` no `pnpm-workspace.yaml` — mesmo resultado, pelo mesmo motivo (a cópia isolada do pnpm pro próprio `@types/node` sempre "ganha" por proximidade na resolução de módulo, hoisting não muda isso). **Fix que funcionou**: uma interface LOCAL mínima (`UploadedFormData`, só com a forma de `.get()` que o código realmente usa) + cast (`z.instanceof(FormData) as unknown as z.ZodType<UploadedFormData>`) — a VALIDAÇÃO em runtime continua sendo um `FormData` de verdade (`instanceof` real), só a FORMA exposta no tipo público do router é estreitada pra um tipo 100% local, sem nenhuma dependência de `undici-types` pra o TypeScript precisar nomear.

### Testing Standards

- Nunca mockar `FormData`/`Blob` — são globais nativos do Node 24, usar os reais nos testes (mesma disciplina de nunca mockar `EmailProvider`/Mailpit em teste de integração, Stories 4.1/4.2).
- `DATABASE_URL`-gated, mesmo padrão de toda `admin/router.test.ts` desde a Story 5.1 — roda contra Postgres real na validação de laboratório, `describe.skipIf` localmente sem banco.
- Processamento sequencial (Task 4.7) faz os testes de ordem (5.3, 5.4, 5.5) serem deterministas sem precisar de nenhum `sort` — a ordem de saída É a ordem de entrada, ponto que os próprios testes devem assertar explicitamente (comparar o array inteiro, não só contar quantos `created`/`duplicate`/`invalid`).
