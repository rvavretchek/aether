# Story 3.1: Árvore de Identidade + Middleware de Enforcement (`requireResource`)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

Como um usuário autenticado de um sistema construído com Aether,
Eu quero que toda procedure tRPC gerada por um Módulo verifique, antes de executar, se eu de fato possuo o Papel/Recurso necessário — negando por padrão quando não possuo,
Para que nenhum Módulo gerado (agora ou no futuro, por qualquer sessão) fique acessível por engano, sem que ninguém precise lembrar de escrever a checagem manualmente.

**Esta é a primeira story do Epic 3** e a **primeira consumidora real de um access token** neste projeto — fecha a AC #10 da Story 2.1 (`AuthProvider.verifyToken`, adiada formalmente pra cá, ver `deferred-work.md`). Constrói só a fundação (schema + extensão tenant-aware + middleware `requireResource`) — o comando `aether-admin generate module` que efetivamente cria Módulos e usa esse middleware fica pra Story 3.2, que depende desta.

## Acceptance Criteria

1. **`AuthProvider.verifyToken` implementado, fechando a AC #10 pendente da Story 2.1 (Zero Trust, NFR2/§8.1).** `apps/api/src/core/auth/auth-provider.ts` ganha `verifyToken(token: string): Promise<{ userId: string; tenantId: string } | null>` na interface; `Argon2AuthProvider` implementa via `jose.jwtVerify` com `algorithms: ['HS256']` **explicitamente fixado** (nunca confiar no `alg` do próprio token — mesmo cuidado já documentado nos Dev Notes da Story 2.1). Token expirado, assinatura inválida, ou `alg` divergente retornam `null` (nunca lançam) — mesmo formato de "credenciais inválidas" já estabelecido.
2. **`ctx.user` populado a partir do header `Authorization: Bearer <token>` (access token nunca em cookie — AC #6 da Story 2.1 continua valendo).** `createContext` extrai o header, chama `verifyToken`; se ausente/inválido, `ctx.user` é `undefined` (não lança — permite que `publicProcedure`s continuem funcionando sem token; a rejeição por falta de autenticação é responsabilidade do `requireResource`, não do `createContext`).
3. **Schema Prisma da árvore de identidade — `Group`, `Role`, `RoleAssignment` escopados por Tenant; `Module`, `ModuleClosure`, `Resource` GLOBAIS (FR-11, AD-6 parcial — só o schema; a escrita atômica via `generate module` é da Story 3.2).** *(Reescrita pós-review, 2026-09-04 — ver Dev Notes "Reconciliação pós-review": `Module` não leva `tenantId`, é estrutura de código compartilhada por toda a instalação, não dado de tenant.)* `ModuleClosure` tem `depth` obrigatório (0 = linha self-referencial), `@@unique([ancestorId, descendantId])`, append-only (nenhum código de produto faz `DELETE`/`UPDATE` nela nesta story — só testes a populam diretamente via Prisma). `Resource.name` é único **globalmente** (não por tenant — resource corresponde a operação de código, não a dado de tenant), padrão `<module-slug>.<ação>` (AD-7) — e agora consistente com `Module` também global (antes da correção, `Resource` global apontava via FK obrigatória pra um `Module` tenant-scoped, o que quebrava RBAC pra qualquer tenant além do "dono" do Module). `RoleAssignment` liga um assignee (`User` OU `Group` — exatamente um dos dois) a um `Role` sobre um `Module` alvo; FKs `userId`/`groupId` usam `onDelete: Cascade` explícito (não o default `SetNull` de FK opcional do Prisma — `SetNull` colidia com a CHECK abaixo).
4. **Extensão Prisma Client tenant-aware (AD-5, `packages/db/extensions/tenant.ts`).** Toda consulta de `Group`/`RoleAssignment` (os únicos models desta árvore que são dado de Tenant) passa por um client Prisma estendido, construído por request a partir do `tenantId` do `ctx.user` verificado — nunca o `PrismaClient` cru de `db/client` pra essas tabelas dentro de `core/authz`. `Module`/`Resource` nunca passam por essa extensão (globais, ver AC #3). Injeta/valida `tenantId` automaticamente nas operações de topo (`findMany`/`findFirst`) dos modelos escopados — filtros relacionais aninhados dentro de uma query maior (ex.: `role:`/`group:` dentro de um `roleAssignment.findFirst`) não passam pelos hooks, só `RoleAssignment.tenantId` é verificado nesses casos (achado do code review, deferred — não explorável hoje).
5. **Middleware `requireResource(resourceId)` central em `core/authz`, default-deny (FR-27, AD-7).** Rejeita com `UNAUTHORIZED` se `ctx.user` não existir (sem token válido). Rejeita com `FORBIDDEN` se existir usuário mas nenhuma `RoleAssignment` (direta no usuário OU via `Group` de que o usuário é membro) cobrir o `Resource` correspondente a `resourceId` — cobertura significa: o `Role` da atribuição concede o `Resource`, E o `Module` alvo da atribuição é o próprio módulo do Resource OU um **ancestral** dele na `ModuleClosure` (herança aditiva simples, FR-12 — nenhum bloqueio/override por nó). Resource desconhecido (nome sem `Resource` correspondente) é erro de configuração (`INTERNAL_SERVER_ERROR`), não `FORBIDDEN` — só `generate module` (Story 3.2) cria `Resource`s, então isso só aconteceria por um bug do próprio gerador.
6. **Orçamento de latência (AD-8) — sem cache.** O middleware faz **dois round-trips sequenciais** (`resource.findUnique` pelo `name`, depois a query de cobertura) — não uma única query ponta a ponta (correção pós-review; o texto original desta AC alegava "uma única query", impreciso). A **query de cobertura** em si é que é única e sem N+1: a subida pela `ModuleClosure` acontece dentro dela via o relacionamento, não em loop de código. Nenhuma camada de cache (in-process ou externa) na frente de nenhuma das duas. Índices obrigatórios presentes: `ModuleClosure(ancestorId, descendantId)` (já coberto pelo `@@unique`), `RoleAssignment` indexado tanto por `(userId, targetModuleId)` quanto por `(groupId, targetModuleId)` (ver Dev Notes — reconciliação do "assigneeId" conceitual da spine com duas FKs concretas do Prisma). Medição real (Task 5.2) precisa cobrir os dois round-trips, não só a query de cobertura isolada.
7. **Lint/format/typecheck/test passam de fábrica.** Mesma barra das Stories 1.1/2.1/2.2 — regenerar via `aether-admin new` e validar de verdade, não só os testes deste repo.

### ⚠️ Reconciliação: `Resource.moduleId` — gap real no ERD da Architecture Spine

O ERD da spine (`ARCHITECTURE-SPINE.md`, diagrama Mermaid) modela `ROLE }o--o{ RESOURCE : "concede"` sem nenhuma relação `Resource`→`Module` explícita — só a convenção de nome (`<module-slug>.<ação>`) amarra um Resource a um módulo, como string. Mas o `requireResource` (AD-7) precisa saber A PARTIR DE QUAL módulo subir a `ModuleClosure` pra verificar herança — derivar isso fazendo parsing do prefixo da string `name` seria exatamente o tipo de "string livre" que a AD-3 evita em outros contextos, e um Resource sem FK real pra Module é uma dependência estrutural codificada só em convenção de nome, frágil. **Resolução desta story:** `Resource` ganha `moduleId` (FK obrigatória pra `Module`) além do `name` — o `name` continua existindo e único globalmente (documentação/debug/AD-7 literal), mas a FK é a fonte de verdade que o middleware de fato consulta. Isso não contradiz nenhuma AC/AD existente, só torna explícito um relacionamento que a spine já pressupõe implicitamente.

### ⚠️ Reconciliação: `RoleAssignment.assigneeId` (spine) vs. duas FKs concretas (Prisma)

AD-8 lista o índice obrigatório como `RoleAssignment(assigneeId, targetModuleId)` — um único campo conceitual "assignee" (Usuário OU Grupo, ver ERD: `USER ||--o{ ROLE_ASSIGNMENT`, `GROUP ||--o{ ROLE_ASSIGNMENT`, ambos como assignee). Prisma não modela FK polimórfica nativamente. **Resolução:** duas colunas `userId String?`/`groupId String?`, exatamente uma setada por linha (validar isso — via `@@check` do Prisma, se a versão instalada suportar; verificar contra `@prisma/client`/`prisma` 7.10.0 real antes de assumir, mesmo cuidado das Stories 2.1/2.2 — se `@@check` não existir na versão real, aplicação valida na escrita e o teste cobre a garantia), com um índice composto por coluna (`[userId, targetModuleId]` e `[groupId, targetModuleId]`) cobrindo, juntos, a mesma necessidade de performance que a spine descreve como um único índice conceitual.

### ⚠️ Reconciliação pós-review: `Module` deixa de ser tenant-scoped (decisão do Boss, 2026-09-04)

Code review de 2026-09-04 (3 layers independentes: Blind Hunter, Edge Case Hunter, Acceptance Auditor) convergiu, sem coordenação entre si, no mesmo achado crítico: `Resource.moduleId` (FK obrigatória, única, adicionada pela reconciliação acima) apontava pra um `Module` que a versão original desta story modelou como tenant-scoped (`tenantId` obrigatório, `@@unique([tenantId, slug])`, seguindo o ERD literal da Architecture Spine — `TENANT ||--o{ MODULE : escopa`). Como `Resource.name` é único globalmente e cada `Resource` só pode apontar pra UM `Module` de UM tenant, qualquer tenant além do "dono" do `Module` referenciado ficava permanentemente `FORBIDDEN` — sem nenhuma `RoleAssignment` possível que alcançasse aquele `moduleId`. Nenhum teste pegou isso porque `require-resource.test.ts` só usava um único `Tenant` por execução.

A raiz é uma contradição real na própria Architecture Spine: **AD-6** diz que `generate module <nome>` roda **uma vez** (tempo de CLI/dev) e insere "a linha" (singular) em `Module` — soa como estrutura de código compartilhada por toda a instalação. Já o **ERD** (diagrama Mermaid) trata `Module` como pertencente a um Tenant. Esta story, ao escrever o schema pela primeira vez, teve que escolher uma leitura — escolheu a do ERD, e isso quebrou a AC #3 original ("`Resource` corresponde a operação de código, não a dado de tenant").

**Decisão do Boss (2026-09-04):** `Module`/`ModuleClosure`/`Resource` passam a ser **globais** — estrutura de código compartilhada por toda a instalação. `generate module` (Story 3.2) cria UMA estrutura, usada por todos os tenants da instalação; isolamento multi-tenant vive só em `RoleAssignment`/`User`/`Group`/`Role`. Bate literalmente com a leitura de AD-6 e resolve a AC #3 sem reescrever sua intenção. A alternativa rejeitada (`Resource` tenant-scoped também, uma linha por tenant) preservaria a leitura do ERD mas abriria um gap de processo novo e não desenhado: como popular `Module`/`Resource` pra um tenant criado DEPOIS que `generate module` já rodou.

**Mudanças concretas:** `Module` perde `tenantId` (`@@unique([tenantId, slug])` → `@@unique([slug])`); `tenant.ts` (`forTenant`) perde os hooks de `module`; migration reescrita à mão (coluna/FK/índice de `tenant_id` removidos de `modules`); `RoleAssignment.user`/`RoleAssignment.group` ganham `onDelete: Cascade` explícito (achado relacionado do mesmo review — `SetNull`, o default do Prisma pra FK opcional, colidia com a `CHECK role_assignments_assignee_check`, travando a exclusão de qualquer `User`/`Group` com atribuição direta); novo teste de integração com 2 Tenants reais provando que o modelo global funciona (`require-resource.test.ts`). **A `ARCHITECTURE-SPINE.md` foi atualizada em conjunto** — ver a nota de reconciliação lá, mesmo padrão da nota já existente sobre EdDSA→HS256 (Story 2.1).

**Validação real concluída:** a migration reescrita à mão e o novo teste de 2 tenants foram reconfirmados contra o Postgres real do Laboratório Integrit (bloqueio inicial de permissão resolvido pelo Boss via `update-config`). Ver Task 5.2 e Debug Log.

### Arquitetura — o que seguir à risca

- **AD-5 (tenant):** toda consulta da árvore de identidade passa pela extensão tenant-aware — `Resource` é a única exceção (global, não escopado por Tenant, AD-7).
  [Source: ARCHITECTURE-SPINE.md#AD-5]
- **AD-6 (só a parte de schema nesta story):** `ModuleClosure` append-only, `depth` obrigatório, linha self-referencial (`ancestorId=id, descendantId=id, depth=0`) — a escrita disso em produção só acontece via `generate module` (Story 3.2); nesta story, testes populam via Prisma direto.
  [Source: ARCHITECTURE-SPINE.md#AD-6]
- **AD-7 (enforcement):** `resource-id` = `<module-slug>.<ação>`, `RESOURCE.name` único globalmente, default-deny, exceção só via procedure explicitamente pública.
  [Source: ARCHITECTURE-SPINE.md#AD-7]
- **AD-8 (latência, sem cache):** p95 < 10ms cobre o middleware inteiro, não só a subquery de ancestralidade — validar contra Postgres real (Task 5.2), não estimar.
  [Source: ARCHITECTURE-SPINE.md#AD-8]
- **AD-4 (composição de Providers):** a extensão tenant-aware e o `requireResource` não são "Providers" no sentido estrito de `providers.ts` (não são pontos de extensão trocáveis por config), mas seguem o mesmo espírito — instanciados/expostos de um único lugar (`core/authz`), nunca reimplementados ad-hoc por módulo.
  [Source: ARCHITECTURE-SPINE.md#AD-4]
- **Convenção de IDs:** UUID v7, colunas físicas `snake_case` via `@map`/`@@map` — mesma convenção de todas as stories anteriores.
