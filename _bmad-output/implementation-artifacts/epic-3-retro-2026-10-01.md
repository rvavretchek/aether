## Findings

Lentes `bmad-review` (adversarial, edge-case-hunter, verification-gap) rodadas sobre o diff consolidado, `also_consider` pedindo atenção especial a fronteiras entre as 3 stories e ao padrão recorrente de bugs só visíveis em validação real. Achados consolidados abaixo (convergência entre lentes = mais confiança, não duplicação).

### F1 — `forTenant`/`$allModels` só guarda `findMany`/`findFirst`; mutações (`update`/`delete`/`upsert`/`findUnique`) não têm isolamento de tenant nenhum
**Fontes:** Adversarial + Edge-Case Hunter (convergente). **Local:** `src/scaffolding/templates/db.ts` (`extensions/tenant.ts`).
AD-5 declara literalmente: "todo acesso a modelo escopado por Tenant passa por um Prisma Client estendido... A extensão injeta/valida `tenant_id` automaticamente" — sem qualificar "acesso" como só-leitura. A implementação cobre 2 dos ~7 métodos relevantes do Prisma. Hoje inofensivo (os únicos módulos gerados até agora só fazem `list`/`create`), mas o próprio texto da story já diz que o model gerado é "um ponto de partida" que o desenvolvedor edita à mão — o primeiro `update`/`delete` adicionado a um `repository.ts` gerado fica sem proteção nenhuma contra acesso cross-tenant, e nada no nome/docs da função avisa disso.
**Disposição:** **fix now** — é uma violação real e específica de AD-5, não uma lacuna cosmética. **Lição:** ao redigir uma regra de arquitetura ("todo acesso... automaticamente"), checar contra a superfície real da API (todos os métodos do Prisma que aceitam `where`), não só os dois métodos que o primeiro módulo gerado usa.

### F2 — Tabela gerada por `generate module` não tem índice em `tenant_id`
**Fonte:** Adversarial. **Local:** `src/codegen/module-migration.ts` (`buildModuleMigrationSql`).
Toda leitura que o próprio scaffold gera (`repository.ts`'s `list()`) filtra por `tenantId` via `forTenant`, mas a `CREATE TABLE` não declara índice nenhum além da PK. Mesmo padrão de cuidado já aplicado a `RoleAssignment` (Story 3.1) para o mesmo tipo de acesso não foi replicado aqui.
**Disposição:** **fix now** — fix de uma linha (`CREATE INDEX`), sem risco.

### F3 — Nenhum teste cobre os comandos reais de `defaultFormatGeneratedCode`/`defaultGeneratePrismaClient`
**Fonte:** Verification Gap. **Local:** `src/cli/commands/generate-module.ts`.
Todo teste que alcança `defaultGenerateOneModule` sobrescreve as duas funções via `options` — nenhum verifica a string de comando real (`pnpm --filter db run generate`, `pnpm exec prettier --write .`). É exatamente o mesmo formato de ponto cego que já causou o bug real do `prisma generate` ausente (achado só na validação de ponta a ponta desta mesma story, depois de 4 camadas de review estático + testes mockados não pegarem nada). `migrate.ts` já tem o padrão de teste correto para seu comando equivalente (`migrate.test.ts:110`) — não foi replicado aqui.
**Disposição:** **fix now** — espelhar o padrão já existente em `migrate.test.ts`.

### F4 — Testes de integração contra o Postgres do laboratório compartilhado nunca limpam as linhas que criam
**Fonte:** Adversarial. **Local:** `router.test.ts` gerado (`src/codegen/module-files.ts`) e `require-resource.test.ts` (`src/scaffolding/templates/authz.ts`).
`beforeEach` cria `Tenant`/`User`/`Group`/`Role`/`RoleAssignment` direto via Prisma, sem `afterEach`/`afterAll`. Confiam só em nomes aleatorizados (`Date.now()`/`Math.random()`) para evitar colisão de unique constraint — nunca deletam o que criaram.
**Disposição:** **ação de infraestrutura compartilhada** (não é só um defeito deste repo — é o Postgres do Laboratório Integrit, usado por este e por projetos irmãos). Crescimento não-limitado de linhas órfãs numa base compartilhada degrada silenciosamente o próprio sinal ("validado contra Postgres real") que esta epic inteira usa como prova de correção. **Fix now**, e — por já ser um padrão estabelecido na sessão — a solução (adicionar `afterEach` com delete cascateando via FK) deve ser compartilhada com os projetos irmãos (Tecton/Tupã/Arandu) se algum deles também gerar dados de teste direto no mesmo laboratório.

### F5 — `prettier --write .` roda no repositório inteiro antes do ponto-de-não-retorno; rollback não desfaz reformatação colateral de arquivos pré-existentes não relacionados
**Fonte:** Edge-Case Hunter. **Local:** `src/cli/commands/generate-module.ts` (`defaultGenerateOneModule`).
Se a migration falhar DEPOIS do `formatGeneratedCode`, o rollback restaura só `schema.prisma`/`root-router.ts`/os arquivos novos — qualquer outro arquivo do projeto que o Prettier tenha reformatado como efeito colateral do `--write .` global fica alterado mesmo com o "rollback" reportado como sucesso. Puramente cosmético (conteúdo semântico idêntico), mas quebra a garantia implícita de "rollback restaura o estado original".
**Disposição:** **defer** — documentar como limitação conhecida, mesmo tratamento já dado à limitação do `_prisma_migrations failed`.

### F6 — `rollback()` engole os próprios erros silenciosamente
**Fonte:** Edge-Case Hunter. **Local:** `src/cli/commands/generate-module.ts` (`rollback()`).
Cada etapa do rollback tem `.catch(() => undefined)` — se a própria reversão falhar parcialmente (ex.: `rm` do `moduleDir` falhar por lock do Windows), o chamador só vê o erro original, sem saber que o projeto pode ter ficado num estado parcialmente revertido.
**Disposição:** **defer** — baixo risco real, mas vale nota no `deferred-work.md`.

### F7 — Janela de mensagem enganosa no retry após sucesso parcial (migrate ok, `prisma generate` falha)
**Fonte:** Adversarial. **Local:** `src/cli/commands/generate-module.ts`.
Se o processo morrer entre `runMigrate` ter sucesso e `generatePrismaClient` completar, um retry do mesmo nome bate na checagem de colisão genérica ("já foi gerado antes?") em vez da mensagem específica que já existe pro caso síncrono ("rode `pnpm --filter db run generate` manualmente"). Janela real porque esse trecho foi deliberadamente colocado FORA do try/catch de rollback (decisão desta mesma story, hoje).
**Disposição:** **defer** — janela rara (precisa de crash no meio exato), recuperação manual ainda é possível.

### F8 — `buildModuleMigrationSql` não tem blindagem própria contra SQL injection — depende inteiramente do regex de outro módulo
**Fonte:** Adversarial. **Local:** `src/codegen/module-migration.ts`.
Função pura, interpola `slug` direto em literais SQL, sem escaping próprio — a segurança de hoje vem 100% de `validateModuleName` (em `generate-module.ts`) ser a única porta de entrada. Relevante porque a story já documenta `--from <arquivo>` como extensão futura planejada (fonte de slugs menos confiável).
**Disposição:** **defer**, com nota para quando `--from` for desenhado.

## Behavior verification

Os 4 itens roteados como **fix now** (ver Action items) foram implementados e validados de ponta a ponta contra o Postgres real do Laboratório Integrit, não só por teste mockado:

- **F1 (forTenant guarda mutações)**: probe dedicado (`prisma.role` tenant-scoped) provou, contra Postgres real, que `forTenant(tenantB).role.update(...)`/`.delete(...)` numa linha do Tenant A retornam `P2025` (registro não encontrado — o merge de `tenantId` no `where` torna a linha invisível pro tenant errado), enquanto `forTenant(tenantA)` no mesmo id funciona normalmente. As 4 combinações (update/delete × cross-tenant/same-tenant) confirmadas.
- **F2 (índice tenant_id)**: `generate module financeiro` rodado de verdade; `pg_indexes` confirma `financeiro_tenant_id_idx` criado junto com a PK.
- **F3 (teste dos comandos default)**: novo teste de integração local (`generate-module-integration.test.ts`) chama `runGenerateModule` sem nenhum override, mockando só `runCommand`, e confirma as duas strings exatas (`pnpm exec prettier --write .`, `pnpm --filter db run generate`) — 85/85 testes locais passando.
- **F4 (cleanup de testes)**: `router.test.ts` gerado (módulo `financeiro`) rodado isolado 1x — contagem de `tenants` idêntica antes/depois (67→67). `require-resource.test.ts`, regenerado do zero num projeto novo (`retro-check`, framework corrigido) pra não herdar o arquivo desatualizado do `/app` já existente — contagem de `modules`/`tenants` idêntica antes/depois (51/67 → 51/67) rodando as 9 cenários.

Efeito colateral real descoberto durante a validação (não um achado do retro, um erro meu de implementação): a extensão de `$allModels` para `findUnique`/`update`/`updateMany`/`delete`/`upsert` quebrou `tsc --build` real contra um projeto regenerado — esses métodos exigem `where`/`data`/`create` em formas que o tipo genérico de `injectTenant` não expressa. Corrigido com um segundo cast (`as typeof args`) só nos métodos que precisam — `findMany`/`findFirst`/`deleteMany` usam `WhereInput` solto e já tipavam certo; adicionar o cast ali virou erro de lint (`no-unnecessary-type-assertion`), também pego rodando `eslint` real contra o projeto regenerado. Ambos corrigidos e revalidados (`tsc --build` + `eslint` limpos).
