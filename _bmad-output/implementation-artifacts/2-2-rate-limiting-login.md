# Story 2.2: Rate Limiting no Login (Proteção contra Força Bruta)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

Como um operador de um sistema construído com Aether,
Eu quero que tentativas repetidas de login com credenciais inválidas para o mesmo email ou IP sejam temporariamente bloqueadas,
Para que um atacante não consiga testar senhas por força bruta contra a procedure `login`, sem depender de Redis nem de infraestrutura além do Postgres já usado pelo `TokenRevocationStore`.

**Esta é a última story do Epic 2** — fecha o FR-28 (parcial: infra do rate limiter + endpoint de login; a parte de redefinição de senha é da Epic 4, reaproveitando a mesma tabela/mecanismo). Depois desta story, Epic 2 pode ser marcado `done`.

## Acceptance Criteria

1. **`RateLimiter` como interface + adapter local (AD-10, mesmo padrão de composição da AD-4).** `apps/api/src/core/auth/` expõe uma interface `RateLimiter` com `isBlocked(identity)`/`recordFailure(identity)`, e uma implementação `PrismaRateLimiter`. Nenhum código de negócio importa `PrismaRateLimiter` diretamente — só via `providers.ts` (mesma regra da Story 2.1, AD-4).
2. **Tabela `RateLimitHit` própria, fisicamente separada de `RefreshToken` (AD-10, literal).** `packages/db/schema.prisma` ganha `model RateLimitHit(identifier, windowStart, count)` — mesmo banco de dados do `TokenRevocationStore` (FR-9), mas **nunca** reaproveitando colunas/tabela dele. Incremento é **atômico** no banco (upsert em `(identifier, windowStart)` únicos) — sem essa atomicidade, requisições concorrentes para o mesmo identificador teriam uma janela de corrida (mesma classe de bug corrigida no code review da Story 2.1 pro TOCTOU do `refresh`).
3. **Identificador composto — email escopado por tenant, IP global (FR-28, "por identificador (ex.: email, IP)").** Uma tentativa checa/registra **dois** identificadores: `email:<tenantId>:<email>` (email já normalizado, minúsculo, do schema Zod da Story 2.1) e `ip:<ip>` (nunca escopado por tenant — um atacante não respeita fronteira de tenant). Bloqueado se **qualquer um dos dois** exceder o limite.
4. **Janela fixa de 15 minutos, limite de 5 tentativas falhas por identificador (baseline OWASP, ver Dev Notes pra pesquisa).** Excedido → a procedure `login` rejeita com `TRPCError({ code: 'TOO_MANY_REQUESTS' })` (mapeia pra HTTP 429 via o `errorFormatter`/`buildProblemDetails` já existente, RFC 9457, Story 1.1) — **antes** de chamar `AuthProvider.authenticate()`, pra não desperdiçar um Argon2id inteiro (~o custo de CPU do próprio ataque) num identificador já bloqueado.
5. **Só tentativa com credenciais inválidas conta pro limite.** Login bem-sucedido nunca chama `recordFailure`. Erro de validação Zod (`BAD_REQUEST`, input malformado) também nunca conta — só o `UNAUTHORIZED` que `authenticate()` retornando `null` produz (Story 2.1, AC #9) incrementa o contador.
6. **Bloqueio não vira um novo vetor de enumeração de usuário (AC #9 da Story 2.1 continua valendo).** Um email que nunca existiu é rate-limited exatamente como um email real — `isBlocked`/`recordFailure` operam sobre a STRING do identificador, nunca consultam se o usuário existe.
7. **Integração via chamada explícita na procedure `login`, não tRPC middleware nem Fastify hook (ver Dev Notes — reconciliação de AD-10).** `core/auth/router.ts` chama `ctx.rateLimiter.isBlocked(...)` no início de `login` e `ctx.rateLimiter.recordFailure(...)` no branch de credenciais inválidas.
8. **Lint/format/typecheck/test passam de fábrica.** Mesma barra das Stories 1.1/2.1 — `pnpm lint`/`pnpm format:check`/`pnpm typecheck`/`pnpm test` sem alteração manual, rodando de verdade contra um projeto gerado por `aether-admin new` (regenerar do zero, não reaproveitar um diretório de teste antigo).

## Dev Notes

### 🎯 Onde este código realmente vive — mesmo lembrete da Story 2.1

Todo path citado nas ACs/Tasks acima (`apps/api/src/core/auth/rate-limiter.ts`, `packages/db/schema.prisma`, etc.) é um path **dentro do projeto que `aether-admin new` gera**, não um arquivo deste repositório. Este repo é o gerador — o código real fica em `src/scaffolding/templates/*.ts`, funções builder retornando `Record<caminhoRelativo, conteúdoDoArquivo>`.

**Estado atual do repo (importante):** a Story 2.1 já está implementada, com code review aplicado, e **commitada** (`adb29eb` — commit isolado especificamente pra separar o diff desta story no code review). Esta story parte desse estado; não redescobrir/reimplementar nada da Story 2.1.

### ⚠️ Reconciliação: "plugin Fastify" (AD-10) vs. chamada explícita na procedure

**Achado desta story — leia antes de implementar.** AD-10 diz literalmente "um único plugin Fastify em `core/auth` aplica rate limit". Um plugin/hook Fastify genérico (`onRequest`/`preHandler`) dispararia pra **toda** requisição HTTP — mas `login` e `system.hello` (e qualquer outra procedure futura) compartilham a **mesma** rota HTTP via `fastifyTRPCPlugin` (`/trpc/:path`), então um hook Fastify não tem como saber, sem inspecionar o path interno do tRPC, que só `login` (e futuramente a redefinição de senha) deve ser rate-limited. Em vez de depender de uma API do tRPC (`.use()` middleware com acesso ao `input` já parseado) cuja forma exata não foi verificada contra a versão instalada (`@trpc/server` 11.18.0) — mesmo cuidado que a Story 2.1 teve com `@prisma/config` (Debug Log, Task 2.3: "API verificada contra o pacote real instalado, não documentação/memória") —, esta story resolve isso com **chamada explícita** de `ctx.rateLimiter` dentro do corpo da procedure `login` (Task 3.4).

Isso **cumpre a intenção real da AD-10** ("Prevents: ... contador em memória por réplica... tabela reaproveitando colunas da tabela de revogação... nunca implementações paralelas"): o mecanismo reutilizável é a classe `PrismaRateLimiter`/interface `RateLimiter`, composta uma única vez em `providers.ts` (mesmo padrão AD-4 já estabelecido) — "o mesmo plugin" da AD-10 é essa composição única, não literalmente um objeto `server.register(...)` do Fastify. Quando a Epic 4 implementar a redefinição de senha, ela reaproveita a MESMA instância/classe, chamando `ctx.rateLimiter` do mesmo jeito — nunca uma segunda implementação paralela. Se, ao implementar, o dev-agent verificar que o tRPC 11.18.0 middleware realmente dá acesso limpo ao input parseado sem gambiarra, pode migrar pra `.use()` como um refactor **depois** que a chamada explícita já estiver funcionando e testada — não é um requisito desta story, é uma opção de polimento.

### Pesquisa: threshold de rate limiting (pesquisa web, verificado 2026-09-02)

OWASP Authentication Cheat Sheet / WSTG recomendam bloqueio temporário após **5 a 10 tentativas falhas**, rate limiting por IP e/ou por conta (idealmente os dois), com lockout medido em minutos (não permanente) — o mesmo espírito de "bloqueio temporário, não erro comum indistinguível" que o FR-28 já pede. Esta story usa o valor mais conservador da faixa: **5 tentativas, janela de 15 minutos**. Constantes nomeadas (`RATE_LIMIT_MAX_ATTEMPTS = 5`, `RATE_LIMIT_WINDOW_MS = 15 * 60 * 1000`), nunca mágicas soltas no código — mesmo padrão de `ARGON2_OPTIONS`/`ACCESS_TOKEN_TTL` da Story 2.1.

Fontes: [OWASP WSTG — Testing for Weak Lock Out Mechanism](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/04-Authentication_Testing/03-Testing_for_Weak_Lock_Out_Mechanism), [OWASP Authentication Cheat Sheet — resumo](https://www.training-central.net/2026/07/09/owasp-authentication-cheat-sheet/).

### ⚠️ NÃO usar `@fastify/rate-limit` nem qualquer plugin de rate limit em memória

Pacotes prontos de rate limiting do ecossistema Fastify são, por padrão, **in-memory por instância** — não sobrevivem a múltiplas instâncias do processo nem persistem entre restarts, exatamente o que a AD-10 explicitly proíbe ("Prevents: ... contador em memória por réplica que não pega ataque distribuído entre instâncias"). Usar um desses seria criar uma segunda implementação paralela à tabela Postgres, violando a própria regra da AD-10. Não adicionar nenhuma dependência nova — esta story não precisa de nenhum pacote npm além do que a Story 2.1 já trouxe.

### Sem cleanup/TTL automático de `RateLimitHit` — corte de escopo deliberado

Linhas antigas (`windowStart` já expirado) nunca são apagadas nesta story — a tabela cresce sem limite. Aceitável pro MVP (volume baixo, ambiente de dev/lab, sem deploy de produção — AD-9); não há infraestrutura de job agendado no projeto ainda pra rodar uma limpeza periódica. Revisitar como um item de `deferred-work.md` quando essa infraestrutura existir — não implementar um cron/scheduler agora só pra isso, seria escopo além do que a AD-10/FR-28 pedem.
