# Review Adversarial — ARCHITECTURE-SPINE.md (Aether) — update AD-11/AD-12

## Método

AD-1..AD-10 já passaram por uma revisão adversarial própria (`review-adversarial.md`, 2026-08-15) e os achados daquela rodada já foram incorporados na Rule atual (namespace de `resource-id`, proibição de raw SQL, exceção de `core/admin`, self-row/`depth` do Closure Table, exceção type-only de `AppRouter`, `common.ts` para schema compartilhado, propagação via `ctx`, budget de latência ponta-a-ponta, `invalid-params` como JSON Pointer, dono do refresh de token, `snake_case` via `@map`). Esta rodada é focada exclusivamente no que a atualização de 2026-10-08/09 adicionou: **AD-11** (Class Table Inheritance para `DirectoryObject`+`User`/`Group`/`Role`) e **AD-12** (`RoleAssignment.subjectId` polimórfico), mais a interação dos dois com **AD-5** (isolamento de tenant via Prisma Client Extension), que é pré-existente mas nunca foi revisitada à luz da nova forma do schema.

Mesmo método da rodada anterior: para cada probe, um par concreto **(Story/sessão A, Story/sessão B)**, construídas independentemente a partir da mesma Rule, cada uma individualmente compliant, que ainda assim produzem artefatos incompatíveis entre si. Severidade: **CRÍTICO** (corrompe dado/segurança/invariante central), **ALTO** (dois stories ficam garantidamente incompatíveis em integração), **MÉDIO** (divergência real, impacto contido), **BAIXO** (cosmético).

## AD-11 — protocolo de criação base+extensão

### Achado U.1 — Proveniência do `id` compartilhado entre base e extensão não é pinada (client-side vs. DB-side UUID v7) — **CRÍTICO**

A Rule de AD-11 fixa o *efeito* ("criar um objeto é sempre criar as DUAS linhas... na mesma transação") mas não fixa o *mecanismo* de como o `id` chega às duas linhas. A Consistency Conventions table fixa `UUID v7 ... @default(uuid(7)) nativo do Prisma desde 5.18` como a convenção de ID — o que sugere geração **no banco**, no momento do insert. Mas um `id` gerado pelo banco só é conhecido *depois* que o insert da linha base retorna — e a forma mais comum/"ingênua" de satisfazer "mesma transação" em Prisma é a API de transação sequencial (`prisma.$transaction([op1, op2])`, forma array), que **não permite** que `op2` use um valor retornado por `op1` (as operações são preparadas e enviadas como um batch independente, sem dependência de resultado entre elas). Isso força, na prática, duas implementações mutuamente incompatíveis:

- **Story A** (ex.: criação de Usuário) gera o UUID v7 **no código da aplicação** (lib `uuidv7`/similar), passando o mesmo `id` explicitamente em `DirectoryObject.create({ data: { id, ... } })` e `User.create({ data: { id, ... } })`, despachados via `$transaction([...])` em forma array — funciona porque o `id` já é conhecido antes de qualquer insert, mas `@default(uuid(7))` do `schema.prisma` fica morto (nunca disparado, já que todo insert sempre fornece `id` explicitamente).
- **Story B** (ex.: criação de Grupo, sessão diferente) lê a mesma convenção de ID e confia no `@default(uuid(7))` do banco — e para encadear o `id` retornado da linha base na linha de extensão, precisa necessariamente de uma **transação interativa** (`prisma.$transaction(async (tx) => { const obj = await tx.directoryObject.create(...); await tx.group.create({ data: { id: obj.id, ... } }); })`). Essa é uma forma de código estruturalmente diferente da de A (callback vs. array), e **a única que de fato funciona** se o default for DB-side — o que já é, por si, uma pista de que a Rule deveria ter fixado isso, em vez de deixar cada sessão redescobrir a mecânica certa (ou errada) sozinha.

Resultado: Usuário e Grupo (dois `objectClass` do mesmo padrão CTI) acabam com proveniência de `id` diferente — um client-gerado, outro DB-gerado — sem que nenhuma Rule tenha sido violada em nenhum dos dois casos ("mesma transação" foi respeitado pelos dois, de formas diferentes). Um teste futuro que assuma "todo `DirectoryObject.id` vem do `@default(uuid(7))`" (ex.: para validar ordenação temporal via UUID v7) passa para Grupo e falha silenciosamente de um jeito sutil para Usuário, caso a lib de geração client-side usada difira da implementação v7 do Prisma/Postgres em bits de relógio/entropia — ordenação por id deixa de ser garantidamente monotônica entre as duas origens misturadas na mesma tabela.

**Tightening sugerido:** AD-11 precisa fixar explicitamente **uma** das duas mecânicas — recomendado: "o `id` é sempre gerado client-side (lib `uuidv7` em `packages/db` ou `packages/shared`) antes de qualquer insert, e passado explicitamente para as duas linhas (base + extensão) na mesma chamada `prisma.$transaction([...])`; `@default(uuid(7))` do `schema.prisma` é só fallback de defesa (scripts manuais/seed), nunca o caminho usado pelo código de produto" — ou o inverso, fixando a transação interativa como único mecanismo. Qualquer um resolve; o que não pode é ficar implícito, porque a Rule atual é satisfeita por ambos.

### Achado U.2 — Política de `ON DELETE` para `RoleAssignment.subjectId → DirectoryObject.id` não está fixada — **ALTO**

AD-11 fixa `ON DELETE CASCADE` só para o par base↔extensão (`DirectoryObject` → `User`/`Group`/`Role`). AD-12 introduz `RoleAssignment.subjectId` como FK para `DirectoryObject.id`, mas nenhuma das duas ADs diz o que acontece com uma linha de `RoleAssignment` quando o `DirectoryObject` (e por cascade, sua extensão) referenciado por `subjectId` é deletado.

**Cenário:** Story A (feature "remover Usuário", FR-14) assume `onDelete: Cascade` também nessa FK — deletar o Usuário remove silenciosamente todas as atribuições de Papel associadas, e a UI é desenhada sem nenhum aviso/confirmação especial ("deletar é só deletar, o resto é cascade automático", coerente com o padrão de cascade que AD-11 já usa em todo lugar). Story B (feature "remover Grupo", sessão diferente) assume o oposto — `onDelete: Restrict` — e constrói a UI de remoção verificando antes se há `RoleAssignment`s pendentes, bloqueando a operação com uma mensagem ("remova as atribuições de papel antes de excluir este grupo"). O `schema.prisma` só pode ter uma dessas policies na coluna física — a migration de quem implementar primeiro decide silenciosamente o comportamento real, e a outra story (cujo código já foi escrito assumindo o comportamento contrário) ou mostra uma mensagem de erro que nunca vai disparar (Restrict assumido, mas é Cascade) ou deixa de mostrar um aviso necessário (Cascade assumido, mas é Restrict, e a operação de exclusão simplesmente falha com uma constraint violation não tratada na UI).

**Tightening sugerido:** AD-12 (ou uma extensão de AD-11) precisa fixar explicitamente a policy de `ON DELETE` para `RoleAssignment.subjectId` (e, por simetria, `RoleAssignment.roleId`) — ex.: "exclusão de um `DirectoryObject` referenciado por `RoleAssignment.subjectId` é `RESTRICT`: a UI de remoção (FR-14) deve checar e revogar atribuições existentes antes de permitir a exclusão, nunca cascade silencioso sobre uma tabela de controle de acesso."

## AD-11 — padrão de query "objeto + campos tipados"

### Achado U.3 — Nenhum helper de join canônico é mandatado; nome(s) da(s) relação(ões) Prisma não é(são) fixado(s) — **ALTO**

A Rule diz: *"Operações genéricas... trabalham via `DirectoryObject.id`; operações específicas de tipo... trabalham via a tabela de extensão correspondente."* Isso descreve **quando** usar qual lado, mas não **como** o join entre os dois é expresso em código — nem o nome do campo de relação no `schema.prisma`, nem se existe um helper compartilhado.

**Cenário:** Story A (tela de listagem de Usuários, FR-14) parte de `DirectoryObject` e inclui a extensão: `prisma.directoryObject.findMany({ where: { objectClass: 'User', tenantId }, include: { user: true } })` — assume um campo de relação `DirectoryObject.user` (e, por simetria ao gerar os próximos tipos, seria `.group`/`.role`, três campos opcionais nomeados por tipo). Story B (resolução de assignee em `core/authz`, consumindo `RoleAssignment.subjectId`) parte do lado oposto: `prisma.user.findUnique({ where: { id: subjectId }, include: { directoryObject: true } })`, assumindo um único campo de relação reverso `User.directoryObject`. Nenhuma das duas é "errada" pela letra da Rule — mas exigem **declarações de relação diferentes** no mesmo `schema.prisma` compartilhado, escritas possivelmente por quem implementou AD-11 pela primeira vez sem saber que um consumidor futuro (Story B) ia precisar do sentido inverso. Se só uma direção foi declarada (comum — Prisma não obriga declarar os dois lados nomeados de forma simétrica, mas o lado "não escolhido" explicitamente pelo primeiro autor tende a ficar com um nome genérico tipo `directoryObject_User` ou nem existir como campo navegável sem um segundo `@relation` dedicado), a segunda story quebra em tempo de compilação (tipo Prisma Client inexistente) e tem que redesenhar o schema — um retrabalho exatamente do tipo que AD-11 diz querer evitar ("cada tipo administrável novo exigindo reescrever... como a Epic 5 fez separadamente").

Mais sutil: mesmo que ambos os sentidos de relação existam no schema, nada impede um terceiro módulo de inventar uma **terceira** forma de obter o mesmo dado — ex.: duas queries separadas sem `include` (`findUnique(DirectoryObject)` seguido de `findUnique(User)` manual, sem usar a relação Prisma de jeito nenhum, só fazendo join "na mão" na camada de aplicação) — compliant com "trabalha via DirectoryObject.id e via a tabela de extensão", mas uma terceira implementação de uma operação que deveria ser uma só.

**Tightening sugerido:** AD-11 precisa nomear o mecanismo canônico — ex.: "toda consulta que precisa do objeto genérico + campos tipados usa um helper único em `core/directory` (`getDirectoryObjectWithExtension(id)` / `listByObjectClass(objectClass)`), que encapsula o include/join; nenhum `repository.ts` de módulo de negócio escreve o join inline." Isso fecha tanto o nome da relação Prisma (interno ao helper, pode mudar sem quebrar consumidores) quanto a proliferação de padrões de consulta divergentes.

## AD-12 — resolução de `subjectId`

### Achado U.4 — "Resolvido por join com `objectClass`" admite pelo menos duas formas de query incompatíveis em extensibilidade — **ALTO**

A Rule de AD-12 fixa o **critério** (objectClass decide o tipo, nunca qual coluna está preenchida) mas não a **forma da query**. Duas formas plausíveis, ambas conformes à letra:

- **Padrão A** ("LEFT JOIN duplo, sempre"): uma única query SQL com `LEFT JOIN User` e `LEFT JOIN Group` incondicionais a partir de `RoleAssignment.subjectId = DirectoryObject.id`, escolhendo em código qual dos dois resultados é não-nulo — útil para quem está otimizando o caminho de enforcement (AD-8, budget p95 <10ms, sem N+1) e quer manter tudo numa ida só ao banco.
- **Padrão B** ("resolve depois"): primeiro lê `DirectoryObject.objectClass`, e só então dispara a query específica do tipo correspondente (`User` ou `Group`) — dois round-trips, mas mais simples e é o padrão natural para quem está construindo a tela de administração (não está no caminho quente de AD-8).

Os dois "resolvem por join com `objectClass`, nunca por qual coluna está preenchida" — a Rule não escolhe entre eles. O problema aparece quando **um terceiro `objectClass` é adicionado** (a própria spine já aponta o candidato — "Custodiante", Deferred de AD-11): quem usa o Padrão A precisa lembrar de adicionar um `LEFT JOIN` a cada call site que o implementou inline (se não houver um helper único — ver Achado U.3, o mesmo problema se repete aqui: múltiplos call sites, cada um precisando ser lembrado manualmente); quem usa o Padrão B só precisa estender o `switch`/`if` num único lugar, **se** esse lugar for de fato único. Hoje nada garante que seja — a Rule não diz que existe uma função `resolveSubject(subjectId)` central; ela só diz qual é o critério de decisão. Dois módulos que precisam saber "este `subjectId` é User ou Group" (ex.: enforcement em `core/authz` e a tela de "quem tem este Papel" em `core/admin`) podem perfeitamente reimplementar a resolução cada um à sua moda — uma usando Padrão A, outra Padrão B — e divergir exatamente no momento em que um terceiro tipo é adicionado: um dos dois caminhos passa a ignorar silenciosamente o novo tipo (Padrão A sem o `LEFT JOIN` novo retorna linhas com ambos os lados nulos para um Custodiante, e o código que escolhe "o não-nulo" não tem nenhum branch para esse caso — falha silenciosa, não erro explícito).

**Tightening sugerido:** nomear explicitamente, em AD-12, uma função de resolução única e seu contrato (ex.: `resolveSubject(subjectId): Promise<{ objectClass: 'User' | 'Group', subject: User | Group }>` em `core/directory`, reaproveitada tanto pelo caminho quente de AD-7/AD-8 quanto pela UI de administração) — e deixar explícito que adicionar um `objectClass` novo exige tocar essa função num único lugar (ponto de extensão nomeado, mesmo espírito do `providers.ts` de AD-4).

### Achado U.5 — `objectClass` como string livre vs. enum tipado não é fixado — contribui para U.4 — **MÉDIO**

O ERD marca `objectClass` como `string "User | Group | Role (AD-11)"` — comentário em prosa, não um enum do Prisma (`enum ObjectClass { User Group Role }`). Builder A declara um enum Prisma real (ganha checagem em tempo de compilação, mas qualquer `objectClass` novo exige migration no enum); Builder B usa `String` puro validado só por Zod na borda (mais barato de estender, mas sem garantia de banco — nenhum CHECK constraint, qualquer bug de digitação tipo `"user"` minúsculo passa pela camada de aplicação se ela não validar). Isso é exatamente a separação "objeto genérico no código vs. garantia real no banco" que `docs/aether-tecton-compatibility.md` (seção "Separação objeto vs. persistência", 2026-10-08) já discute para `attributes JSONB` — mas a mesma pergunta nunca foi respondida para a própria coluna `objectClass`, a peça mais crítica do padrão CTI (é o discriminador usado por toda resolução de U.3/U.4). Duas extensões de tipo escritas em sessões diferentes podem literalmente usar valores de string com casing diferente (`"User"` vs `"USER"`) se não houver enum de banco forçando um conjunto fechado de valores — quebrando qualquer `WHERE objectClass = 'User'` escrito por quem assumiu o padrão contrário.

**Tightening sugerido:** fixar `objectClass` como Prisma `enum` (não `String` livre) — consistente com o resto da spine preferir garantia real de banco (mesmo racional de AD-11 para `Role.name`/`User.email`); documentar que adicionar um `objectClass` novo inclui migration do enum como parte do trabalho manual já descrito em Deferred.

## AD-5 × AD-11/AD-12 — isolamento de tenant sobre o schema CTI

### Achado U.6 — `tenantId` duplicado nas tabelas de extensão não é declarado, e o ERD contradiz a própria Rule de AD-11 — **CRÍTICO**

AD-11 exige que `Role.name` e `User.email` mantenham `@@unique([tenantId, name])` / `@@unique([tenantId, email])` **na tabela de extensão** ("na tabela de extensão em vez do modelo raiz"). Mecanicamente, uma constraint `@@unique` do Prisma só pode referenciar colunas do **mesmo modelo** — não existe `@@unique` composto cruzando duas tabelas sem uma view/trigger. Logo, para essa Rule ser sequer implementável como constraint real de banco (que é a garantia que AD-11 explicitamente diz que o Aether *não* abre mão), `tenantId` precisa existir como **coluna própria, duplicada**, em `User`/`Group`/`Role` — não só em `DirectoryObject`.

Isso nunca é dito explicitamente em lugar nenhum da spine. Pior: o ERD (bloco `erDiagram`, linhas de atributos) mostra `tenantId` **só** no box de `DIRECTORY_OBJECT`; os boxes de `USER`/`GROUP`/`ROLE` listam apenas `id` e o campo tipado próprio (`email`/`name`), sem `tenantId` — o próprio diagrama contradiz o que a Rule em prosa exige mecanicamente. Dois builders resolvendo essa lacuna de forma independente:

- **Story A** adiciona `tenantId` à tabela de extensão (forçado pela mecânica do Prisma), e — percebendo que agora `User`/`Group`/`Role` são "modelos escopados por Tenant" no sentido literal da Rule de AD-5 ("todo acesso a modelo escopado por Tenant passa por um Prisma Client estendido... a extensão injeta/valida `tenant_id` automaticamente") — atualiza a Prisma Client Extension de tenant (`packages/db/extensions/tenant.ts`) para incluir `User`, `Group`, `Role` na lista de modelos interceptados, ao lado de `DirectoryObject`.
- **Story B** também adiciona `tenantId` à extensão (mesma necessidade mecânica), mas **não** toca a Tenant Extension — raciocínio plausível: "AD-11 diz que operações específicas de tipo trabalham via a tabela de extensão, mas o isolamento de tenant real já é garantido no nível de `DirectoryObject` (todo acesso genérico passa por lá) — a coluna `tenantId` na extensão existe só para a constraint de unicidade funcionar, não precisa duplicar o filtro de query também." Qualquer código futuro que consulte `User`/`Role`/`Group` **diretamente** (e AD-11 não só permite como recomenda isso para "operações específicas de tipo", ex.: "validar nome de Papel" — um `prisma.role.findFirst({ where: { name } })` direto, sem passar por `DirectoryObject`) **não recebe nenhum filtro de tenant** nesse caminho — vaza Papéis/Usuários/Grupos de outros tenants para qualquer query que não inclua `tenantId` manualmente no `where`.

Os dois builders resolveram a mesma Rule de forma individualmente defensável; o resultado é uma condição de corrida arquitetural onde o isolamento de tenant (AD-5, NFR crítico) depende de qual sessão escreveu a extensão por último, e nenhum teste de "dois tenants simultâneos" pega isso se os dois builders também escreverem seus próprios testes assumindo o próprio modelo mental (exatamente o padrão já visto no Achado 5.1 da rodada anterior — raw SQL não coberto — e na reconciliação de Story 3.1, "achado independente de 3 layers de code review, sem nenhum teste de 2 tenants simultâneos pra pegar antes").

Há ainda um risco inverso, também não coberto: se a Tenant Extension for implementada de forma genérica via `$allModels`/introspecção de schema ("todo modelo que tiver uma coluna `tenantId` recebe o filtro automaticamente", um padrão comum e mais robusto que uma lista manual), ela passaria a filtrar **qualquer** modelo futuro que ganhe uma coluna chamada `tenantId` por qualquer outro motivo — reabrindo exatamente o problema que a reconciliação da Story 3.1 já fechou (`Module`/`ModuleClosure`/`Resource` são deliberadamente GLOBAIS, sem tenant). Nada na spine diz se o mecanismo de interceptação é por **lista explícita de modelos** (manual, precisa de disciplina a cada novo `objectClass`/tabela) ou por **introspecção de shape** (automático, mas genérico demais e já colidiria com AD-5/reconciliação de Module se um `tenantId` aparecer em uma tabela que deveria ficar global) — essa escolha de mecanismo nunca foi feita, nem antes nem depois do AD-11/12, e a atualização torna a ambiguidade ativa pela primeira vez (antes de AD-11, só havia um punhado fixo de modelos tenant-scoped, hardcoded; agora o conjunto cresce a cada `objectClass` novo, manual, sem gerador — ver Deferred "`generate directory-object`").

**Tightening sugerido:** (a) o ERD precisa mostrar `tenantId` explicitamente nos boxes `USER`/`GROUP`/`ROLE`, não só em `DIRECTORY_OBJECT` — fechando a contradição entre Rule e diagrama; (b) AD-5 precisa de uma cláusula nova (ou AD-11 precisa estendê-la): "a lista de modelos interceptados pela Tenant Extension é explícita e mantida à mão (`DirectoryObject`, `User`, `Group`, `Role`, `RoleAssignment`, ... — nunca por introspecção automática de shape/coluna), e todo novo `objectClass`/tabela de extensão que carregar `tenantId` **deve** ser adicionado a essa lista como parte do mesmo trabalho manual já exigido por AD-11 (schema + router + testes + entrada na lista da Tenant Extension)."; (c) fixar que toda query direta a uma tabela de extensão (ex.: "validar nome de Papel") passa necessariamente pelo client Prisma estendido — nunca por um client não-escopado — mesmo quando a operação é "específica de tipo" e não passa por `DirectoryObject.id`.

### Achado U.7 — AD-8 ainda referencia a coluna obsoleta `assigneeId`, nunca reconciliada por AD-12 — **ALTO**

AD-12 identifica textualmente que a spine (AD-8) já citava um índice `RoleAssignment(assigneeId, targetModuleId)` com um único campo de assignee, e que isso era uma **divergência não corrigida** entre a spine e o código real (Story 5.5 implementou `userId`/`groupId`). AD-12 resolve a divergência introduzindo `subjectId` como a coluna real — mas o texto da própria Rule de **AD-8**, na seção Invariants & Rules, nunca foi editado: ainda diz, ao pé da letra, *"Índices obrigatórios cobrem toda tabela tocada pelo caminho crítico: `ModuleClosure(ancestorId, descendantId)`, `RoleAssignment(assigneeId, targetModuleId)`..."* — `assigneeId` continua lá, uma coluna que, pós-AD-12, **não existe** (foi substituída por `subjectId`).

**Cenário:** Story A implementa o índice obrigatório de AD-8 e, ao perceber que `assigneeId` não existe no schema (só `subjectId`, via AD-12), silenciosamente cria o índice como `RoleAssignment(subjectId, targetModuleId)` — correto, mas é uma correção não registrada, feita ad-hoc por quem notou a inconsistência. Story B, implementada por uma sessão/agente que segue a Rule de AD-8 mais literalmente (ou que não tem o contexto completo de AD-12 na janela de contexto no momento — um risco realista para qualquer sessão de dev-agent que carregue só o trecho de AD-8 relevante ao seu story, sem reler a spine inteira), tenta criar o índice exatamente como escrito, falha ao encontrar a coluna, e "resolve" adicionando uma coluna gerada/alias `assigneeId` só para satisfizer o nome literal do índice — uma terceira coluna supérflua, nunca pedida por nenhuma AD, que nenhuma outra parte do sistema usa.

**Tightening sugerido:** editar o texto de AD-8 agora, como parte desta mesma atualização, trocando `RoleAssignment(assigneeId, targetModuleId)` por `RoleAssignment(subjectId, targetModuleId)` — a reconciliação que AD-12 descreve em prosa precisa necessariamente tocar o texto de AD-8 também, não só narrar o achado. Enquanto isso não acontece, qualquer sessão que leia só AD-8 (sem o contexto de AD-12) está lendo uma Rule factualmente errada.

| U.6 | AD-5 × AD-11 | `tenantId` duplicado na extensão não declarado; ERD contradiz a Rule; lista de modelos tenant-scoped da Tenant Extension sem mecanismo fixado | CRÍTICO |

| U.5 | AD-11 | `objectClass` como string livre vs. enum tipado não fixado (contribui para U.4) | MÉDIO |

**Veredito geral:** a atualização (AD-11/AD-12) é sólida na decisão de modelo de dados, mas deixa o mesmo tipo de lacuna de "mecanismo não especificado" que a rodada anterior encontrou em AD-6 — e, diferente da rodada anterior, um dos achados (U.6) não é só uma ambiguidade a fechar: é uma **contradição interna já presente no documento** (Rule de AD-11 exige mecanicamente uma coluna que o próprio ERD da mesma atualização não mostra), com risco real de vazamento cross-tenant se resolvida da forma "conservadora" (não tocar a Tenant Extension). Nenhum dos 7 achados invalida a direção do CTI/FK polimórfica — todos são fecháveis com texto adicional nas ADs existentes, sem reabrir a decisão de schema em si.
