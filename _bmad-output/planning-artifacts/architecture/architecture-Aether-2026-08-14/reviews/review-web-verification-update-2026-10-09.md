## Per-claim verification

| # | Implicit claim in AD-11/AD-12 | Verified against | Verdict |
|---|---|---|---|
| 1 | Extension table (`User`/`Group`/`Role`) can have `id` be simultaneously its own `@id` **and** the `@relation` FK field pointing at `DirectoryObject.id` — a true shared-primary-key 1:1 relation ("also PK of the extension") | Web: Prisma's own **new, Prisma-7-specific doc page** `prisma.io/docs/orm/prisma-schema/data-model/table-inheritance` names and documents exactly two patterns for this problem — **STI** (one table, optional columns) and **MTI** (parent + child tables). Separately, `github.com/prisma/prisma/discussions/15990` confirms the shared-PK variant AD-11 actually wants (`id Int @id` + `@relation(fields:[id], references:[id])`) is achievable, but **only if the back-relation on the parent side is optional** (`Profile?`, not `Profile`) — Prisma cannot enforce "exactly one child row must exist" at the DB/schema level for this shape. | **CONFIRMED FEASIBLE, with a documented divergence.** The pattern AD-11 specifies works in Prisma 7.x schema syntax, but it is not the pattern Prisma's own newly-published "Table Inheritance" guidance recommends for this exact scenario — see Discrepancy #1 below. |

## Discrepancies summary

1. **MEDIUM — AD-11's shared-primary-key extension-table pattern diverges from Prisma's own newly-published "Table Inheritance" docs, without the spine acknowledging the divergence or its practical consequence.** Prisma 7's docs (a page that did not exist in this form for v6, confirming it's fresh v7-era guidance) recommend MTI with a *separate* child PK + `@unique` FK specifically so the parent↔child relation can carry normal referential guarantees; the shared-PK variant AD-11 specifies is reachable in Prisma syntax, but **forces the back-relation on `DirectoryObject` (e.g. `user DirectoryObject.user?`) to be optional** — Prisma cannot enforce "a `DirectoryObject` with `objectClass='User'` always has exactly one matching `User` row" at the schema/DB level. AD-11 already mitigates the *practical* risk by mandating same-transaction dual-row writes in application code ("Criar um objeto é sempre criar as DUAS linhas... na mesma transação"), so this is not a blocker — but the spine should say explicitly that this invariant is enforced by application code, not by Prisma/Postgres, since that's a direct, checkable consequence of choosing shared PKs over Prisma's documented MTI shape. Recommend either (a) adding one sentence to AD-11 naming this as a deliberately-accepted trade-off, or (b) a line in the eventual migration story's Dev Notes.
2. **LOW — extension tables' `id` field can no longer carry `@default(uuid(7))`.** Because `id` becomes the FK back to `DirectoryObject.id` under the shared-PK pattern, the extension table's `id` must be supplied explicitly from the parent's freshly-generated id inside the creation transaction, not generated independently. This is a natural, unsurprising consequence of the chosen pattern (not a Prisma limitation) but AD-11's text doesn't spell it out; worth a one-line callout for whoever writes the migration story, so it isn't rediscovered mid-implementation the way the `userId`/`groupId`→`subjectId` drift in AD-12 was rediscovered this session.

No HIGH-severity findings. Neither AD-11 nor AD-12 names a library/version that is wrong, non-existent, or incompatible with the already-pinned Prisma 7.x — the only real finding is that AD-11's specific relational shape is a valid-but-non-default Prisma idiom, which the spine should own explicitly rather than leave implicit.

## Positive findings (checked and cleared)

- The Class Table Inheritance / "base + per-type extension" pattern **is** a real, nameable, currently-documented Prisma concept (Prisma's own docs call the closest analog "Multi-Table Inheritance"), not a pattern invented from training-data assumption.
- `onDelete: Cascade` on the base→extension relation is proven to work in this exact generated schema today (same mechanism already shipped for `RoleAssignment.user`/`.group`), so AD-11's delete rule is not a new, unverified assumption.
- AD-12's "join on `objectClass`, never on which column is filled" design is independently confirmed to be the correct way to route around Prisma's well-documented lack of native polymorphic-relation support — and matches a limitation the project's own code comments had already identified independently in Story 5.5, i.e. the new AD is consistent with, not contradicting, prior reality-checked work in this repo.
- No partial/conditional unique index claim is actually made anywhere in AD-11/AD-12 (the task brief flagged this as something *to check for*; it is simply absent from the text, so there is nothing to verify or flag).
- Prisma 7.x itself remains current (v7.7.0 shipped April 2026, still the current major as of this review date) — consistent with the Stack section's existing pin, no new drift introduced by this update.
