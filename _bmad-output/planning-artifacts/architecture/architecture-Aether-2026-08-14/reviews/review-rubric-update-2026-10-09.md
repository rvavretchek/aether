# Review — ARCHITECTURE-SPINE.md, update AD-11/AD-12 (2026-10-09)

**Scope:** rubric walk of the AD-11 (Class Table Inheritance: `DirectoryObject` base + per-type extension) / AD-12 (`RoleAssignment.subjectId` polymorphic FK) update against the good-spine checklist, with emphasis on internal consistency of the two new ADs and their interaction with AD-5 (tenant isolation), AD-6 (Module-as-code-node), AD-7 (enforcement middleware), and AD-8 (latency budget + required indexes).

**Verdict:** Not clean — the update is well-motivated and the ERD/Capability Map/Deferred bookkeeping was mostly done correctly, but AD-11 and AD-12 each leave an unresolved, enforceable-rule-breaking gap: AD-11 implicitly requires a `tenantId` column on the extension tables (to make its own stated `@@unique([tenantId, name/email])` constraints possible) without ever saying so, which is exactly the fact AD-5's tenant-isolation mechanism depends on and that AD-5's text was never touched to confirm; and AD-8's Rule still names a column (`assigneeId`) that AD-12 explicitly obsoletes in favor of `subjectId`, without AD-8 being corrected. These are real divergence points the next session (or a different agent) would trip over.

## Findings, ranked

### 1. [Critical] AD-11 is internally inconsistent about where `tenantId` lives, and never reconciles this with AD-5

AD-11 (lines 104-108) describes the extension tables as holding only `id` (FK/PK to `DirectoryObject.id`) plus "suas próprias colunas tipadas com constraint real" — and then states, in the same sentence, that `Role.name` keeps `@@unique([tenantId, name])` and `User.email` keeps `@@unique([tenantId, email])` **on the extension table**. A `@@unique` in Prisma can only reference columns that exist on that model. Nothing in AD-11 says `tenantId` is duplicated onto every extension table — the ERD block (lines 209-226) reinforces this reading: `DIRECTORY_OBJECT` is the only entity with a `tenantId` field; `USER`/`GROUP`/`ROLE` are shown with only `id` and their one typed attribute, no `tenantId`.

As written, the Rule is not enforceable: either (a) the extension tables silently need a denormalized `tenantId` column that AD-11 forgot to state (the codebase already has precedent for exactly this move — `RefreshToken.tenantId` is denormalized from `User` today, per the comment in `src/scaffolding/templates/db.ts` lines 103-107 — so this is a one-line fix), or (b) the per-tenant uniqueness has to be expressed some other way (e.g. a partial/expression index joining to `DirectoryObject`, which Prisma's schema language can't express declaratively and would need hand-written migration SQL, same workaround already used for the `role_assignments_assignee_check` CHECK).

This same gap directly undermines **AD-5**. AD-5 (lines 68-72) relies on one mechanism for every tenant-scoped model: a `$allModels` Prisma Client extension (`forTenant`, `src/scaffolding/templates/db.ts` lines 680-746) that injects `tenantId` into the `where` of *every* query, unconditionally, for every model. If `User`/`Group`/`Role` extension tables genuinely have no `tenantId` column, every `db.user.findMany(...)`, `db.group.findFirst(...)`, `db.role.update(...)` issued through `forTenant(...)` breaks at the Prisma-client-validation level (`Unknown argument tenantId`) the moment AD-11 ships — a hard regression of the exact invariant AD-5 exists to protect, with zero acknowledgment in either AD. The fix is the same one-liner as above (denormalize `tenantId` onto every extension table), but nothing in this update states it, and AD-5's own text, and its Capability Map row (line 237: "FR-2, FR-11, §8.1 Isolamento de tenant … Governed by AD-5"), were left untouched even though the shape of every tenant-scoped model AD-5 governs just changed.

**Why this matters for the rubric:** this is precisely the kind of "real divergence point for the level below" the spine exists to fix, and precisely what "Every AD's Rule is enforceable and actually prevents its stated divergence" is checking for — AD-11's Rule, read literally, cannot be implemented without a decision AD-11 never makes, and that missing decision is load-bearing for AD-5.

### 2. [High] AD-8's required index still names the wrong column — not updated for AD-12

AD-8 (lines 86-90) lists the enforcement middleware's required indexes as `ModuleClosure(ancestorId, descendantId)`, `RoleAssignment(assigneeId, targetModuleId)`, and the Papel↔Recurso join. AD-12 itself (line 112) points out that `assigneeId` was always a conceptual placeholder — the real Story 5.5 schema used `userId`/`groupId` — and AD-12's entire Rule (line 114) is to replace those two columns with one real column, `subjectId`. AD-8 was not touched by this update: its Rule still says `assigneeId`, a name that has never existed in the schema and that AD-12 does not introduce either. The index AD-8 now requires should read `RoleAssignment(subjectId, targetModuleId)`.

This is a second, narrower instance of the same class of problem as Finding 1: an AD whose Rule is supposed to be directly actionable (an index to create) names a column that doesn't match the schema anywhere, old or new. Left as-is, a future session implementing "the index AD-8 requires" either has to privately resolve the naming (same kind of silent, unrecorded reconciliation the pre-existing Module/Tenant note and the EdDSA→HS256 note exist to avoid) or creates the wrong index. Minor silver lining: collapsing `userId`/`groupId` to one `subjectId` column means AD-8's original intent — *one* composite index — becomes achievable for the first time (today's schema needs two indexes, per the comment in `db.ts` lines 266-277, specifically because of the two-nullable-column design AD-8's text never matched). That makes this an easy, mechanical fix, which is exactly why leaving it undone in this update is a miss.

### 3. [Medium] AD-12 trades away a real DB constraint without naming a replacement, undercutting AD-11's own stated rationale

The current schema enforces "assignee is exactly one of User or Group" with a real Postgres CHECK constraint (`role_assignments_assignee_check`, `(user_id IS NOT NULL) <> (group_id IS NOT NULL)`, see `db.ts` lines 587-593). AD-12 replaces the two nullable FKs with a single `subjectId` FK to `DirectoryObject.id` — a plain FK only guarantees "this row exists in `DirectoryObject`," not "this row's `objectClass` is `User` or `Group`." Nothing stops `subjectId` from pointing at a `Role`'s `DirectoryObject` row, or (once a `Custodiante` objectClass exists per the Deferred roadmap) at an unintended type, with only application code — not the database — standing in the way.

AD-11's entire justification for choosing CTI over Tecton's AD-2 JSONB-bag approach is explicitly "mantém essas garantias reais no banco" (line 107). AD-12 quietly gives one of those real guarantees back without saying so, and without naming the standard fix (a composite FK against a `(id, objectClass)` unique index on `DirectoryObject`, with `objectClass IN ('User','Group')` enforced alongside it) or accepting the regression explicitly as a tradeoff. Given the update is dated the same session as AD-11 and leans on AD-11's "we don't give up real constraints" framing, this is worth a line either closing the gap or owning it as a conscious, scoped exception.

### 4. [Low-medium] `objectClass` discriminator type is never fixed

AD-11 and the ERD both describe `objectClass` only in prose ("User | Group | Role") — neither states whether it's a Prisma `enum` (like the existing `ResourceKind`) or a free-text `String`. Every downstream invariant in AD-11/AD-12 (which extension table a row belongs to, how `subjectId` is resolved by "join com `DirectoryObject.objectClass`," line 114) depends on this value being constrained to a closed, correctly-spelled set. Without an enum, a typo'd `objectClass` is a silent, undetectable divergence between rows that look alike. This is a small, mechanical gap (the codebase already has the `ResourceKind` enum precedent to copy), but it's the kind of "whole dimension left silent" the rubric flags.

### 5. [Low] No explicit marker that this is forward-looking, not yet applied to the brownfield code

The two earlier reconciliation notes in this document (EdDSA→HS256 in Stack, Module/Tenant scoping in Structural Seed) both explicitly say what the spine used to say, what the code turned out to need, and which one won. AD-11/AD-12 introduce a schema shape that is a strict rewrite of the already-implemented, already-shipped Epic 5 schema (`src/scaffolding/templates/db.ts` still defines concrete `User`/`Group`/`Role` models and `RoleAssignment.userId`/`groupId`, migrated as recently as `20261007000000_add_role_name_unique`) — but unlike those two precedents, nothing here flags that this is a pending migration against real, already-generated code rather than a decision being made before any code exists. `docs/aether-tecton-compatibility.md` (line 83) does say the final schema shape was deferred to "uma sessão de arquitetura dedicada" and that a migration story is still "a ser criada," so the intent is clear from that companion doc — but the spine itself, read on its own, gives no signal that `src/scaffolding/templates/db.ts` and `admin.ts` need a follow-up story before AD-11/AD-12 are real. Worth a short Deferred bullet or inline note naming the migration as outstanding work, the same way AD-6's append-only/no-reparent constraint got its own Deferred bullet.

## What the update got right

- AD-11 and AD-12 are each dated and each carry a clear, specific "Prevents" list grounded in an actual code-vs-spine divergence (the Story 5.5 `userId`/`groupId` vs. AD-8's `assigneeId`), not an invented one.
- AD-6 is explicitly carved out of AD-11's scope ("`Module` … fica fora deste padrão"), and that carve-out is consistent with AD-6's own text — no contradiction there.
- The ERD block was updated (DirectoryObject + three extension entities, `ROLE_ASSIGNMENT.subjectId` relationship line, per-entity constraint annotations) and carries a reconciliation footnote in the same style as the pre-existing Module/Tenant note.
- The Structural Seed file tree line for `schema.prisma` was updated to name `DirectoryObject+{User,Group,Role} (AD-11)`.
- The Capability Map row for FR-11/12/13/14 was updated to list AD-11 and AD-12 alongside AD-6/7/8.
- The Deferred section gained an AD-11-specific bullet (`generate directory-object`) correctly scoped as roadmap, not something that should have been decided now.
- Cross-reference sourcing to `docs/aether-tecton-compatibility.md` is accurate: that document's 2026-10-08 entries do say the Aether authored the CTI-with-real-constraints refinement and that Role becomes first-class, matching what AD-11 claims.

## Recommendation

Before treating this update as settled, resolve Findings 1–3 (they're mechanically cheap — denormalize `tenantId` onto each extension table and say so in AD-11; fix AD-8's column name to `subjectId`; either add the composite-FK/CHECK for `subjectId`'s objectClass or explicitly accept the regression) and pick up Findings 4–5 as low-cost cleanup in the same pass.
