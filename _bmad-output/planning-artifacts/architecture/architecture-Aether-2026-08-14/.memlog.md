- (decision) Paradigma: Hexagonal / Ports & Adapters por Módulo. Cada Módulo (FR-3) isola domínio de infraestrutura atrás de portas próprias; router tRPC e repository Prisma são adapters. Binds: geração de módulo (FR-3), todos os módulos de negócio. Prevents: módulos com lógica de domínio acoplada direto a Prisma/tRPC, divergência de estrutura interna entre módulos gerados por agentes diferentes.
- (decision) Topologia frontend: SPA client-side (Vite + React Router, modo data router). Sem SSR/meta-framework. Binds: FR-1, FR-4. Prevents: acoplar Aether à opinião de roteamento de um meta-framework; introduzir um segundo servidor Node no MVP (conflita com NFR de instância stateless, §8.1).
- (decision) Estrutura de repo: monorepo com pnpm workspaces (apps/web, apps/api, packages/shared para Zod schemas e tipos compartilhados). Binds: FR-1, FR-3, FR-17. Prevents: duplicação/dessincronização de schema Zod entre front e back; symlink manual.
- (decision) Wiring de providers de extensão (AuthProvider, SecretsProvider, TokenRevocationStore, futuros KeyCustodyProvider/WorkflowEngineProvider): factory explícita num módulo de composição único (ex.: providers.ts) monta implementações concretas a partir de config/env; código consumidor importa a instância, nunca a classe concreta. Sem container de DI reflexivo (sem tsyringe/Inversify). Binds: FR-10, FR-18, FR-26, todas as interfaces de extensão §9.1. Prevents: resolução implícita em runtime difícil de rastrear por um agente de IA; import direto da implementação concreta pelo código de negócio.
- (decision) Isolamento de tenant: Prisma Client Extension que injeta/valida tenant_id automaticamente em toda query de modelo escopado, construída por request a partir do contexto tRPC autenticado — nunca client Prisma global. Binds: FR-2, FR-11, NFR §8.1. Prevents: query mal escrita num Módulo gerado vazando dado de outro Tenant; amarração a feature específica de banco (RLS descartado por isso, mesmo raciocínio que já descartou ltree).
- (decision) Enforcement de permissão (FR-27): middleware tRPC central + procedure declara o Recurso exigido na geração (ex.: .use(requireResource('invoice:edit'))). Middleware resolve usuário autenticado, sobe a Closure Table a partir do Módulo alvo em 1 query, verifica cobertura por Papel concedido (herança aditiva, FR-12), default-deny. Gerado uma vez, reutilizado por todos os módulos. Binds: FR-3, FR-11, FR-12, FR-27. Prevents: handler esquecer de checar autorização; divergência de verificação entre módulos gerados por agentes diferentes.
- (decision) Envelope operacional do MVP: sem alvo de deploy/infra de produção formal. MVP cobre apenas dev local (aether-admin dev + Docker Compose de dev, FR-23) e configuração externalizada por ambiente (FR-6). Deploy de produção (provider, Dockerfile hardened) fica Deferred, consistente com corte já fechado no PRD/Brief (§6.2 Fast-follow).
- (decision) Módulo de código (gerado por FR-3) e Módulo da árvore de identidade (FR-11) são o mesmo objeto: 'generate module <nome>' cria o código E o nó correspondente na árvore, na mesma operação, sem passo manual extra. Binds: FR-3, FR-11, Glossário. Prevents: código gerado sem nó correspondente na árvore, ou nó de árvore sem módulo de código — dessincronia entre os dois conceitos que o Glossário já trata como um só.
- (version) Servidor HTTP: Fastify (via adapter oficial @trpc/server/adapters/fastify). Binds: FR-4, FR-16. Prevents: mistura de Express e Fastify entre módulos/serviços gerados em momentos diferentes.
- (decision) Performance do enforcement (FR-27, resolvendo PRD §11 questão aberta #1): meta NFR explícita — consulta de ancestralidade via Closure Table indexada, p95 < 10ms em escala de dev/pequena equipe — com índice composto obrigatório na tabela de fecho (ancestor_id, descendant_id). Sem cache (in-process ou Redis) no MVP. Binds: FR-11, FR-27, NFR §8.1. Prevents: cache in-process por réplica quebrando revogação imediata (FR-9) ou introduzindo Redis fora do escopo já fechado; meta de performance ficar indefinida contra pedido explícito do PRD.

RoleAssignment.userId/groupId (duas colunas separadas, Story 5.5) viram um unico subjectId apontando pro DirectoryObject (User ou Group) - simplifica o discriminated union atual.
